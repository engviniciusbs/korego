# Conexão de agentes por OAuth (MCP) — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Um agente local conecta ao `/mcp` do KoreGO só com a URL: o navegador abre a tela de autorização do painel, o usuário confirma com 2FA e o agente recebe tokens OAuth.

**Architecture:**
- O binário passa a servir também um servidor de autorização OAuth 2.1, com metadados RFC 9728/8414, registro dinâmico RFC 7591, PKCE S256 e refresh rotativo.
- A lógica pura (lista de retornos, PKCE, normalização, saneamento do registro) fica no pacote novo `internal/oauth`.
- Cada conexão aprovada é uma linha de `api_tokens` (`kind = 'oauth'`). Assim `RequireToken`, a auditoria, a lista e a revogação continuam valendo.
- A tela de consentimento é uma página estática do Next (`/autorizar/`) que usa a sessão e o 2FA existentes.

**Tech Stack:** Go 1.27, chi, SQLite (migrações em `internal/store/migrations`), go-sdk MCP v1.8.0 (tipos em `oauthex`, cliente `auth.AuthorizationCodeHandler` no e2e), Next.js (export estático), React Query, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-14-mcp-oauth-design.md`

- `internal/node/proxy` TestEnsure_StartsWhenPortsFree e TestEnsure_SkipsPullWhenImagePresent já falham no `main` neste ambiente. Ignore os dois.
- Mensagens, comentários e textos de UI em pt-BR, no tom do código existente. Commits seguem o padrão `feat(oauth): …` e terminam com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Origem canônica: `https://<domínio do painel>`, só com certificado ativo (`proxy.CertActive`), lida de `domains.Service.Panel`. **Nunca** de `r.Host`. Sem origem, todo endpoint OAuth responde 404 `NOT_FOUND`.
- `resource` canônico = origem + `/mcp`. `issuer` = origem.
- Endpoints `/oauth/*` e `/.well-known/*`: exigem `requestIsHTTPS(r)` (senão 403 `TOKEN_REQUIRES_HTTPS`); sem cookie e sem CSRF; nenhum cabeçalho CORS.
- Retornos permitidos: loopback `http://127.0.0.1`, `http://localhost` e `http://[::1]`, com qualquer porta e qualquer caminho, sem query, fragmento ou userinfo; `https://vscode.dev/redirect` e `https://insiders.vscode.dev/redirect`, exatos. **Nunca** `vscode://`, `vscode-insiders://` ou outros esquemas. O retorno do Cursor fica como gancho vazio (ver Task 2).
- Prazos: código de autorização 60 s e uso único; token de acesso 1 h; janela do refresh anterior 60 s; pedido pendente 10 min; até 256 pedidos pendentes; cliente nunca autorizado expira em 30 dias; até 200 clientes nunca autorizados (o mais antigo sai); validade da conexão 30 ou 90 dias (padrão 90).
- Limites por IP (IPv6 agrupado por /64): registro 10/h; authorize 30/min; falhas no `/oauth/token` 10/min com bloqueio de 15 min.
- Segredos: código, `client_id`, id do pedido e tokens usam 32 bytes aleatórios em base64url (43 caracteres). Acesso `kg_…`, refresh `kgr_…`. Só o hash SHA-256 vai para o banco.
- As rotas de aprovação ficam em `mountSessionOnly`, **nunca** em `mountCore`.

## Review Focus

1. **Bloqueio do IP por uso normal:** um cliente com acesso vencido, um token revogado ou uma sondagem sem token, repetidos 10 vezes, não podem deixar o IP bloqueado para um token manual válido. Teste na Task 4.
2. **Retorno do authorize com cliente ou `redirect_uri` inválido:** a resposta é uma página de erro 400 e nunca `Location`, nem para um `redirect_uri` "parecido" (`http://localhost.evil.com/cb`). Teste na Task 6.
3. **Domínio do painel removido depois da conexão:** todo endpoint OAuth passa a 404 e o `/mcp` continua aceitando os tokens já emitidos até vencerem, sem pânico. Testes nas Tasks 5 e 7.
4. **Duas renovações concorrentes com o mesmo refresh:** exatamente uma rotação vence o CAS; a outra, dentro de 60 s, ainda recebe um par válido e a conexão não é revogada. Teste na Task 3.
5. **Usuário que acabou de entrar digita o mesmo código do login na tela de autorização:** recebe `INVALID_CODE` e a tela mostra o aviso de aguardar o próximo código. Testes nas Tasks 6 e 8.

### Task 3: `auth.Tokens` — emissão OAuth, renovação e tokens vencidos

**Files:**

**Interfaces:**

- Produces:
  - `auth.ErrStaleToken`: token bem formado cujo hash corresponde a uma linha, mas que está vencido, revogado, com o acesso expirado ou é o acesso anterior. `Validate` passa a devolvê-lo nesses casos; `ErrNoToken` fica só para mal formado ou hash desconhecido.
  - `auth.ErrRefreshReuse`.
  - `auth.AccessTTL = time.Hour` e `auth.RefreshGrace = 60 * time.Second`.
  - `auth.OAuthPair{Access, Refresh string; ExpiresIn time.Duration}`.
  - `(*Tokens) IssueOAuth(ctx, userID int64, clientName, clientID string, ttl time.Duration) (OAuthPair, store.APIToken, error)`. Nome único: `clientName`, depois `clientName (2)` até `(20)` quando dá `ErrConflict`. O nome é cortado para caber em 64 runas com o sufixo. `Kind = "oauth"`, `ExpiresAt = now + ttl`, `AccessExpiresAt = now + AccessTTL`.
  - `(*Tokens) Refresh(ctx, refresh, clientID string) (OAuthPair, store.APIToken, error)`:
    - refresh mal formado ou desconhecido, `client_id` diferente, conexão revogada ou `ExpiresAt` passado: `ErrNoToken`;
    - refresh igual ao `RefreshHash` atual: rotação normal (`KeepPrev = false`);
    - igual ao `PrevRefreshHash`, com `now - RotatedAt <= RefreshGrace`: rotação com `KeepPrev = true`;
    - igual ao `PrevRefreshHash` fora da janela: `RevokeAPITokenByID` e `ErrRefreshReuse`;
    - `ErrConflict` no CAS: relê a linha e tenta mais uma vez pelas mesmas regras (a concorrência cai na janela).
    - O novo `AccessExpiresAt` é `min(now + AccessTTL, ExpiresAt)`.
  - `(*Tokens) RevokeByID(ctx, id int64) error`.
  - `Validate`: além das regras atuais, `AccessExpiresAt` passado dá `ErrStaleToken`. Hash desconhecido consulta `APITokenByPrevAccessHash`: se achar, dá `ErrStaleToken`; senão, `ErrNoToken`.
